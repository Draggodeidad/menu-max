# Reporte de auditoría y pruebas e2e — MenusMax

Fecha: 10 de noviembre de 2026. Alcance: código disponible en el workspace, sin corregir la aplicación ni conectar servicios externos.

## Resumen ejecutivo

MenusMax tiene todas las rutas principales y una base navegable con validaciones y estados simulados. Sin embargo, el negocio todavía no puede publicar y el pedido enviado no llega con sus datos al seguimiento ni al panel. La salida prometida a WhatsApp tampoco existe; además, catálogo, modalidades y tema no se reflejan en el menú público. Es una demostración parcial, todavía lejos de cumplir las dos conversiones principales del MVP.

## Contexto y discrepancias

El prompt dejó el objetivo y la lista de flujos como marcadores sin rellenar. Se tomó como referencia `apps/web/PRODUCT.md` y `apps/web/DESIGN.md`: negocios de comida en México crean y publican un menú digital; los comensales consultan el menú, piden como invitados y siguen su pedido; el negocio gestiona pedidos, productos y ajustes. No es posible afirmar si esta interpretación coincide con requisitos que no se proporcionaron.

La UI consume mocks y no llama a una API de negocio real. El repositorio, sin embargo, **no es literalmente solo frontend**: contiene `apps/api`, un servidor Hono con `GET /health`, y `pnpm dev` arranca tanto web como API. Además, SvelteKit ejecuta loads y form actions en su servidor. No hay base de datos, autenticación real ni contratos compartidos implementados; el proyecto indica que son dependencias futuras, no tareas para activar ahora. `apps/web/AGENTS.md` menciona el adaptador de Cloudflare, pero `apps/web/vite.config.ts` usa `adapter-auto`; la compilación termina y advierte que no detectó un entorno de producción compatible.

Se probaron Chromium desktop de 1280 × 800 y móvil de 375 × 812. Los 32 `fixme` son 16 escenarios pendientes, cada uno en ambas resoluciones; **no son pruebas que hayan pasado**. Antes de marcarlos se reprodujo cada fallo y se conservaron [32 capturas con test, resolución y causa probable](evidencia/INDICE.md). Una primera ejecución de infraestructura no pudo abrir el navegador de Playwright; se instaló Chromium y se repitió, por lo que no se computa como fallo del producto.

La suite incluye navegación por las diez rutas, flujos de borrador y acceso simulado, carrito, mesa, avance en panel, validaciones, estados vacíos, cerrado, carga lenta y errores disponibles; comprueba lectura pública sin JavaScript y ausencia de desbordamiento horizontal en los tamaños indicados. Durante el diagnóstico, Axe ejecutó reglas WCAG 2 A/AA y 2.1 A/AA en ocho pantallas y el checkout con productos; en la suite final el caso de catálogo queda como `fixme`; también se comprueba foco con teclado en acceso. Son comprobaciones parciales: no sustituyen revisión manual completa de contraste, lector de pantalla, todos los controles o dispositivos reales. Las fuentes de Google se neutralizan en los tests para que no dependan de Internet, por lo que la descarga y apariencia real de fuentes quedan fuera de esa verificación.

```sh
pnpm install --frozen-lockfile
pnpm exec playwright install chromium --only-shell
pnpm test:e2e
```

En Linux, si faltan bibliotecas del navegador, puede requerirse `pnpm exec playwright install-deps chromium` conforme al entorno. La configuración levanta Vite local en `127.0.0.1:4179`; no reutiliza un servidor ajeno. `pnpm validate` y el CI actual no incluyen `test:e2e`, por lo que debe ejecutarse por separado. El reporte JSON, trazas y capturas de fallos nuevos quedan en `test-results/` (ignorado por Git); las capturas de la auditoría se conservan en `docs/feedback/evidencia/`. Los tests usan la marca interna de hidratación de Svelte en **modo desarrollo**, de modo que habría que revisar `e2e/helpers.ts` si cambia esa implementación.

## Inventario técnico y de pantallas

- **Stack y scripts:** monorepo pnpm 11.4.0; Node 24–26; SvelteKit 3, Svelte 5, TypeScript, Vite 8, Tailwind 4, bits-ui/shadcn-svelte, lucide y QRCode. El router es el de archivos de SvelteKit en `apps/web/src/routes`. Raíz: `pnpm dev`, `pnpm build`, `pnpm check`, `pnpm lint`, `pnpm test` (antes de esta auditoría solo pruebas de API) y ahora `pnpm test:e2e`. La web no tenía script de tests ni configuración e2e; la API tiene `apps/api/test/health.test.ts` con Node/tsx.
- **Estructura:** `apps/web/src/routes/` contiene pantallas, loads y actions; `apps/web/src/lib/components/` componentes compartidos; `apps/web/src/lib/server/demo.ts` datos y lógica demo; `apps/web/src/lib/cart.svelte.ts` carrito contextual con `localStorage`; `apps/api/` contiene la API de salud. No había `docs/tasks/` ni pruebas Playwright/Cypress previas.
- **Negocio:** `/` landing; `/crear` borrador y publicación pendiente; `/entrar` acceso simulado; `/app/listo` QR de ejemplo; `/app` pedidos; `/app/catalogo` productos; `/app/ajustes` tema, servicio, zonas, equipo y QR.
- **Comensal:** `/m/[slug]` menú; `/m/[slug]/pedido` carrito y checkout; `/pedido/[token]` seguimiento. `?mesa=n` conserva el número de mesa.
- **Componentes clave:** `MenuView.svelte` muestra el menú y se reutiliza en la vista previa de ajustes; `Phone.svelte` presenta vistas previas; `OrderCard.svelte` ejecuta las acciones del panel; `ProductImage.svelte` usa el placeholder; `StorefrontSkeleton.svelte` y los skeletons de cada ruta representan carga; `ui/` contiene primitivas botón, input y label. La vista previa de `/crear` es una implementación propia, no `MenuView`.
- **Mocks y persistencia:** `demo.ts` concentra negocio, productos, pedidos, catálogo y ajustes con tipos temporales; cookies `demo_avance`, `demo_catalogo` y `demo_ajustes` mantienen cambios por navegador en `/app`. El carrito y el borrador usan `localStorage`. `/crear` y la landing también contienen ejemplos inline. Hay banderas de desarrollo para vacío, lentitud, cierre, errores concretos y estados de seguimiento; no cubren el error de carga del menú público.

## Flujos observados hoy

1. **Negocio nuevo:** landing → `/crear` con nombre → edición/vista previa y borrador local. Se detiene en publicación deshabilitada; `/app/listo` puede visitarse aparte y muestra datos de ejemplo.
2. **Negocio existente:** `/entrar` valida formato y contraseña no vacía → `/app`; también se puede abrir el panel directamente. Aceptar y avanzar pedidos base se refleja tras recargar en ese navegador. Catálogo y ajustes guardan cambios simulados locales al panel.
3. **Comensal:** menú → agregar producto y variantes → checkout con recoger, domicilio o mesa → validaciones → token de seguimiento. La redirección funciona, pero el seguimiento muestra un pedido fijo, el panel no recibe el pedido y no existe salida a WhatsApp.
4. **Estados:** panel y catálogo ofrecen vacío/error/carga; ajustes ofrece error/carga; menú muestra vacío/cierre/carga y checkout simula producto agotado. El error de carga del menú queda pendiente (H13).
